WHAT RELINK DOES

目の前にあるモノが、
何者で何ができるかを
Webから発見する。

RELinkは、物理Entityのための共通の発見経路です。Physical Anchorから現在のEntity Descriptionへ進み、Capabilityと利用可能なInterfaceを人間と機械の両方に示します。

RELinkは新しいIoT通信規格やWeb API規格ではありません。既存のHTTP(S)、WoT、BLE、MQTT、OPC UA、vendor APIなどへ到達するための、Physical Entity側の共通入口です。

01 / WHAT RELINK ADDS

A COMMON ENTRY POINT

URLではなく、
その先の意味をそろえる。

02 / REFERENCE LAB

PHYSICAL PATH

概念だけでなく、
Pico 2 Wまでつなぐ。

RELink Pico 2 W Reference Labは、既存のResolver、AR-XML、Web Runtime、Capability API、Gateway、物理デバイスを分離したまま接続する最小L1参照ラボです。

DISCOVERY / DESCRIPTION PLANE
Anchor→Resolver→AR-XML→Web Runtime

load() はDescriptionの取得・解析・公開です。ロードしただけで機器は動きません。

EXPLICIT EXECUTION PLANE
Human / Web App→RuntimeCapability.invoke()→Capability API→Pico 2 W

invoke() が明示的に要求されたときだけ、Capability APIを経由して物理Entityへ届きます。

PHYSICAL OUTPUT

Onboard LED

light.setState によるLED ON / OFFを対象にした実機経路。

PHYSICAL INPUT

RP2350 temperature

temperature.read による内部温度の読み取り。正確な室温計測を主張するものではありません。

IMPLEMENTATION BOUNDARY

Not L2 or production security

Trust、認証、認可、完全準拠の証明ではありません。明示操作のL1参照経路を扱います。

03 / EXISTING TECHNOLOGIES

COMPLEMENT, NOT REPLACEMENT

既存技術を置き換えず、
物理Entityからつなぐ。

RELinkの役割は、個々のtransport、API、Thing Description、商品識別子を統一することではありません。物理Entityを起点に、それらへの共通入口を提供することです。

技術主に解決するものRELinkとの関係
QR / NFC URL物理物からURLへの移動URL先の意味やCapabilityは共通化しない
GS1商品・物流対象の識別operational Capabilityの発見が主目的ではない
WoT TDThingのinteraction記述Physical Anchorから現在のTDへ到達する経路とは別の役割
OpenAPI個別Web APIの操作・データ記述Physical EntityやAnchorを扱わない
MQTT / OPC UA / BLEdevice messaging・産業・近接通信Capabilityを実行するInterfaceになり得る
RELinkPhysical EntityからCapabilityへの共通解決経路実際のAPI・transportは既存技術を利用可能

EXAMPLE 同じ light.setState Capabilityが、HTTPS POST、WoT TD、BLE、vendor-specific adapterという複数Interfaceを持てます。現在のWeb Runtimeの中心はHTTP(S)ですが、これはRuntime実装の境界であり、RELink仕様全体の制限ではありません。

04 / WHEN RELINK HELPS

USE IT WHEN DISCOVERY MATTERS

単純なAPIより、
Entityの発見が必要なとき。

1台のdevice、1つのapplication、既知のAPIだけで完結するなら、REST APIを直接使う方が簡単です。RELinkはそこに余分な層を足すためのものではありません。

APPLICATION / WEB

事前知識のないEntityを扱う

個別APIをあらかじめ組み込まず、Capabilityを見つけて利用したい開発者。

DEVICE / PRODUCT

既存実装を捨てずに入口を足す

API、SDK、WoT、BLE、MQTTなどを維持したまま、Physical AnchorとDiscoveryを追加したいメーカー。

SYSTEM INTEGRATION

複数ベンダーを意味で統合する

通信方式や製品差を越えて、EntityとCapability単位で接続したい人。

AGENT / AUTOMATION

機械可読な操作候補を得る

現実空間のEntityが何をできるかを取得し、Application側の方針で明示実行したい開発者。

05 / HOW IT WORKS

SMALL, SEPARATE RESPONSIBILITIES

発見と実行を、
同じものにしない。

最小のWeb-native baselineは、Physical Anchor、UUID、Resolver、HTTPS、Entity Descriptionです。Resolverは小さく、Interfaceの呼び出しには関与しません。

01
STABLE PHYSICAL REFERENCEPhysical Anchor / UUID

QRやNFCなどに置ける、Entityへの安定した物理入口。

02
DNS-LIKE INDIRECTIONResolver → 303 See Other

UUIDを現在のEntity Description Locationへ解決するだけ。AR-XMLを解析せず、Capabilityを実行しません。

03
ENTITY INTERFACE DESCRIPTIONAR-XML

Entity、Capability、Input Contract、Result Contract、Interfaceを機械可読に記述します。

04
RUNTIME + APPLICATIONDiscover, then explicitly invoke

Web RuntimeはCapabilityを公開し、HumanまたはApplicationが明示要求した場合だけInterfaceを呼び出します。

Entity ≠ LocationCapability ≠ InterfaceDescription ≠ ExecutionResolution ≠ Authentication
