01 / CONCEPT

リンクするのは、
ページではなく能力です。

今日のWebは「モノについてのページ」へリンクできます。しかし、そのモノが今何をできるか、どう呼び出すか、何が必要かまでは共通の方法で表現できません。

RELinkは、エンティティの意味と実行インターフェースを分離しながら結びます。アプリやエージェントは専用連携を知らなくても、能力を発見して適切な方法で実行できます。

01

Entity ≠ Location

存在そのものの識別子と、現在の文書URLを分離します。

02

Capability ≠ Interface

「何ができるか」と「どう実行するか」を別の層として扱います。

03

Semantics before Platform

ブラウザ、ロボット、モバイルを越えて意味を共有します。

03 / AR-XML EXAMPLE

CONCRETE CONTRACT

「何ができるか」と
「どう呼ぶか」を分ける。

この例では、温度を読むという意味的なCapabilityを、HTTP GET Interfaceへ結び付けています。Interfaceが変わっても、Capabilityの意味は変わりません。

<ar-entity
  xmlns="https://relink.dev/ns/arxml/core/0.1"
  version="0.1">
  <capabilities>
    <capability
      id="temperature"
      type="…/temperature/read/1">

      <result>
        <outputs>
          <output name="temperature"
                  type="number" />
        </outputs>
      </result>

      <interfaces>
        <interface type="http"
                   method="GET"
                   endpoint="/api/temperature" />
      </interfaces>
    </capability>
  </capabilities>
</ar-entity>
WHAT
temperature.read温度を読み取るCapability
RETURNS
numbertemperatureというOutput
HOW
HTTP GET/api/temperatureを呼び出すInterface
PRINCIPLE
Capability ≠ Interface

04 / ONE JOURNEY

ひとつのAnchorから、
ひとつのActionまで。

RELinkの最小の体験は、現実世界の対象に触れ、能力を理解し、実行するまでの連続した流れです。

  1. 01Touch

    QR・NFC・URL・IDから、エンティティへの手がかりを得る。

  2. 02Resolve

    Resolverが永続的なidentityと最新の文書位置を返す。

  3. 03Discover

    RuntimeがAR-XMLを読み、利用可能なCapabilityを公開する。

  4. 04Invoke

    要件を評価し、選択したInterfaceから実際の処理を呼び出す。

05 / USE CASES

FROM LINK TO ACTION

現場ごとに違うモノを、
同じ流れで扱う。

RELinkが共通化するのは製品固有の操作ではなく、対象を見つけ、能力を理解し、条件を確かめて実行するまでの流れです。

◎

Asset ID→Entity→Diagnostics
  • 設備保全
  • 点検
  • 遠隔支援
