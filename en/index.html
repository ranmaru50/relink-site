01 / CONCEPT

Link the
capability,
not just the page.

Today’s Web can link to a page about a thing. It does not provide one shared way to describe what that thing can do now, how to call it, or what it requires.

RELink connects entity meaning and execution interfaces while keeping them separate. An application or agent can discover a capability and choose an appropriate way to invoke it without a device-specific integration.

01

Entity ≠ Location

Separate the identity of an entity from the URL of its current description.

02

Capability ≠ Interface

Keep “what can be done” separate from “how it is invoked.”

03

Semantics before Platform

Share meaning across browsers, robots, mobile clients, and other runtimes.

04 / AR-XML EXAMPLE

CONCRETE CONTRACT

Separate what it can do
from how to call it.

This example connects the semantic Capability “read temperature” to an HTTP GET Interface. The meaning stays the same when the Interface changes.

<ar-entity
  xmlns="https://relink.dev/ns/arxml/core/0.1"
  version="0.1">
  <capabilities>
    <capability
      id="temperature"
      type="https://example.org/capabilities/temperature/read/1">
      <result>
        <outputs>
          <output name="temperature" type="number" />
        </outputs>
      </result>
      <interfaces>
        <interface type="http" method="GET" endpoint="/api/temperature" />
      </interfaces>
    </capability>
  </capabilities>
</ar-entity>
LOCAL ID
temperatureShort document-local reference
SEMANTIC CAPABILITY ID
https://example.org/capabilities/temperature/read/1Global identifier for the Capability meaning
RETURNS
numberThe temperature Output
HOW

05 / CURRENT & TARGET FLOW

CURRENT & TARGET

Today’s baseline,
tomorrow’s full flow.

These two flows distinguish what the Web Runtime can run today from the target architecture that starts with a Physical Anchor.

01 / CURRENT BASELINE

Run from an AR-XML URL

BASELINE VALIDATED

The current Web Runtime path. Loading AR-XML does not execute a Capability. A Human or Application discovers a Capability and explicitly requests invocation.

LOADAR-XML URL→DISCOVERWeb Runtime→REQUESTHuman / Application→INVOKECapability
02 / TARGET ARCHITECTURE

Resolve from a Physical Anchor

RESOLVER IMPLEMENTED / L1 NEXT

The L1 flow now moves into acceptance validation with the Frozen Resolver Core 0.1 and its reference implementation. An Anchor UUID resolves to the current HTTPS Description Location, which is handed to the Runtime.

TOUCHAnchor→RESOLVEResolver→LOADAR-XML→EXECUTERuntime→RESULTCapability

BOUNDARY The Resolver specification and reference implementation are available, while external L1 acceptance and integration validation continue. Direct AR-XML loading remains the L0 path.
