WHAT RELINK DOES

Discover what the thing
in front of you is — and
what it can do.

RELink is a common discovery path for physical Entities. It starts from a Physical Anchor, reaches the current Entity Description, and presents Capabilities and usable Interfaces to both people and software.

RELink is not a new IoT transport or Web API standard. It is a Physical Entity-side entry point to existing HTTP(S), WoT, BLE, MQTT, OPC UA, and vendor APIs.

01 / WHAT RELINK ADDS

A COMMON ENTRY POINT

Make the meaning
after the URL consistent.

QR and NFC can already give someone a URL. The missing shared rule is whether that URL leads to a page, an API, an admin screen, a WoT TD, or an Entity Description — and how a Consumer discovers a Capability there.

EXISTING WEB IS ENOUGH FORPhysical object → QR / NFC → URL

A stable URL and ordinary HTTP redirect can reach a current location. They do not standardize the meaning or Capabilities at that location.

RELINK ADDSPhysical Anchor → Entity → Capability → Interface

RELink defines a path from a physical Anchor to the current Description and semantic Capabilities. Existing technologies can still execute the work.

02 / REFERENCE LAB

PHYSICAL PATH

Not only a concept:
connect it to a Pico 2 W.

The RELink Pico 2 W Reference Lab connects an existing Resolver, AR-XML, Web Runtime, Capability API, gateway, and physical device while preserving their separate responsibilities.

DISCOVERY / DESCRIPTION PLANE
Anchor→Resolver→AR-XML→Web Runtime

load() retrieves, interprets, and exposes a Description. It does not operate a device.

EXPLICIT EXECUTION PLANE
Human / Web App→RuntimeCapability.invoke()→Capability API→Pico 2 W

Only an explicit invoke() request reaches the physical Entity through the Capability API.

PHYSICAL OUTPUT

Onboard LED

A physical path for LED ON / OFF through light.setState.

PHYSICAL INPUT

RP2350 temperature

Internal temperature reading through temperature.read. It is not a claim of accurate room-temperature measurement.

IMPLEMENTATION BOUNDARY

Not L2 or production security

This covers an explicit-execution L1 reference path, not Trust, authorization, full conformance, or production security.

03 / EXISTING TECHNOLOGIES

COMPLEMENT, NOT REPLACEMENT

Do not replace existing tech.
Connect it from the Entity.

RELink does not attempt to unify each transport, API, Thing Description, or product identifier. Its role is to provide a common entry from a Physical Entity to those existing technologies.

TechnologyMain concernRelation to RELink
QR / NFC URLMove from a physical object to a URLDoes not standardize the meaning or Capabilities at the URL
GS1Identify products and logistics objectsOperational Capability discovery is not its main concern
WoT TDDescribe Thing interactionsDifferent from a physical path to the current TD
OpenAPIDescribe one Web API and its dataDoes not model a Physical Entity or Anchor
MQTT / OPC UA / BLEMessaging, industry, or proximity communicationCan become a Capability Interface
RELinkCommon resolution from a Physical Entity to a CapabilityUses existing APIs and transports where appropriate

EXAMPLE One light.setState Capability may offer HTTPS POST, WoT TD, BLE, or a vendor-specific adapter. The current Web Runtime is HTTP(S)-centred; that is an implementation boundary, not a restriction of the RELink architecture.

04 / WHEN RELINK HELPS

USE IT WHEN DISCOVERY MATTERS

Use it when discovering
the Entity matters.

For one device, one application, and one known API, a direct REST API is simpler. RELink is not an extra layer for that situation.

APPLICATION / WEB

Use Entities without prior API knowledge

Developers who want to discover a Capability rather than embed every individual API in advance.

DEVICE / PRODUCT

Add an entry point without replacing existing work

Vendors who want to retain APIs, SDKs, WoT, BLE, or MQTT and add a Physical Anchor plus Discovery.

SYSTEM INTEGRATION

Integrate vendors by meaning

People who need to connect devices by Entity and Capability across transport and product differences.

AGENT / AUTOMATION

Obtain machine-readable options

Developers who need to discover what an Entity can do, then apply application policy before explicit invocation.

05 / HOW IT WORKS

SMALL, SEPARATE RESPONSIBILITIES

Do not make discovery
and execution the same thing.

The smallest Web-native baseline is Physical Anchor, UUID, Resolver, HTTPS, and Entity Description. The Resolver stays deliberately small and never calls an Interface.

01
STABLE PHYSICAL REFERENCEPhysical Anchor / UUID

A stable physical entry to an Entity, suitable for QR, NFC, and similar media.

02
DNS-LIKE INDIRECTIONResolver → 303 See Other

Resolves a UUID to the current Entity Description Location. It does not parse AR-XML or invoke a Capability.

03
ENTITY INTERFACE DESCRIPTIONAR-XML

Machine-readable Entity, Capability, Input Contract, Result Contract, and Interface description.

04
RUNTIME + APPLICATIONDiscover, then explicitly invoke

The Web Runtime exposes Capabilities; a Human or Application calls an Interface only through an explicit request.

Entity ≠ LocationCapability ≠ InterfaceDescription ≠ ExecutionResolution ≠ Authentication
