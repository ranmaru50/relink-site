01 / SYSTEM ARCHITECTURE

FROM ANCHOR TO DEVICE

Connect resolution,
description, and execution.

The Resolver does not operate a device. AR-XML is not UI. The Runtime does not act on its own. An ordinary HTTPS API controls the device at the edge.

IMPORTANT The Resolver returns an AR-XML Description Location. It does not choose a Capability API or device IP, parse AR-XML, or invoke a Capability.

01Entity ≠ Location

Separate a room or light’s canonical identity from its current AR-XML URL.

02Capability ≠ Interface

Separate the meaning “change the light state” from the POST endpoint.

03Description ≠ Execution

Retrieving AR-XML does not operate a device.

04Resolution ≠ Authentication

A successful 303 response does not grant control permission.

02 / SCENARIO

ONE ROOM, TWO ENTITIES

Turn on the light, read the room,
set a target temperature.

The Web Application presents discovered Capabilities and calls `invoke` only after a person or application requests the operation.

    Read an Anchor URL from the room’s QR code or NFC tag.

  2. 02

  3. 03

    The Web Runtime loads, parses, and validates AR-XML, then exposes Capabilities to the Application.

  4. 04

  5. 05

  6. 06

  7. 07

  8. 08

04 / ENTITY DESCRIPTION

AR-XML CORE DRAFT 4

Describe semantic Capabilities
and HTTP Interfaces.

AR-XML is an Entity Interface Description Language. It does not describe buttons, automation conditions, or device implementation code.

LIGHT / SET STATEPOST JSON · NO OUTPUT
<ar-entity
  xmlns="https://relink.dev/ns/arxml/core/0.1"
  version="0.1">
  <category>home.room</category>
  <capabilities>
    <capability
      id="set-light"
      type="https://example.org/capabilities/light/set-state/1">
      <inputs>
        <input name="on" type="boolean" required="true" />
      </inputs>
      <result>
        <representations>
          <representation media-type="application/json" />
        </representations>
      </result>
      <interfaces>
        <interface type="http" method="POST"
          endpoint="../api/light/state" encoding="json" />
      </interfaces>
    </capability>
  </capabilities>
</ar-entity>
TEMPERATURE / GET CURRENTGET · MULTI-OUTPUT JSON

  id="get-temperature"
  type="https://example.org/capabilities/temperature/get-current/1">
  <result>
    <outputs>
      <output name="temperature" type="number" unit="Cel" />

Capability semantics are independent of an Interface. A future binding can preserve the same semantic contract: “change the light state.”

05 / RELATIVE INTERFACE URL

STANDARD URL RESOLUTION

Use the final AR-XML URL,
not the Web App URL.

A relative Interface endpoint is resolved against the final AR-XML Document URL after redirects, using standard URL resolution.

FINAL AR-XML DOCUMENT URLhttps://home.example/arxml/living-room.xml
+
RELATIVE INTERFACE../api/light/state
=
RESOLVED INTERFACE URLhttps://home.example/api/light/state

Do not use the host Web Application, original Anchor, or Resolver URL as the base. The Web Runtime resolves endpoints from the final Description URL for both L0 and L1 loading. Broader external L1 integration remains under validation.

06 / WEB RUNTIME

IMPLEMENTATION UNDER CONTROL

The Runtime exposes.
The Application decides.

This example follows the current public API. `load` reads AR-XML but never auto-executes a Capability.

load AR-XML→parse→validate→evaluate→expose Capability
CURRENT PUBLIC API / L0EXPLICIT INVOCATION
const runtime = new ARRuntime();

// The baseline accepts the final Description URL directly.
const document = await runtime.load(
  "https://home.example/arxml/living-room.xml"
);

const light = document.getCapability("set-light");
if (!light) throw new Error("Capability not found");

// Invoke only after a Human / Application decision.
await light.invoke({ on: true });
Human↓Web Application↓Web Runtime↓Capability↓HTTP Interface↓Device / Gateway

09 / SECURITY & RESPONSIBILITY

DISCOVERY IS NOT AUTHORITY

Being discoverable does not
mean being operable.

A public Anchor UUID or successful resolution does not prove control authority. The Capability API must enforce final authorization.

Anchor URL≠authorization credential
Resolver resolution≠authentication
AR-XML load success≠permission to control
Capability discovery≠execution authorization
RUNTIME

Expose Capabilities

Validate AR-XML and present availability and Interfaces to the Application while respecting HTTPS, CORS, mixed-content, and Runtime network policy.

APPLICATION

Decide UI and Policy

Decide who sees “Light ON,” “Brightness 50%,” or “Target 22°C,” and which operation to invoke.

BACKEND

Authenticate and Authorize

Enforce authentication, authorization, and application policy before forwarding an allowed request to the device.

10 / APPLICATION AUTOMATION

ONE EXPLICIT RULE

Automation belongs to the Application,
not the Runtime.

The Application reads temperature, evaluates its own condition, and explicitly invokes another Capability.

Application→temperature.getCurrent→28°C→if temperature > 27→temperature.setTarget(24)
const reading = document.getCapability("get-temperature");
const target = document.getCapability("set-target-temperature");
if (!reading || !target) throw new Error("Capability not found");

const result = await reading.invoke({});

// The Application decides; the Runtime invents no condition.
if (Number(result.values.temperature) > 27) {
  await target.invoke({ target: 24 });
}
